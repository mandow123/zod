# KAI 卡时结算手续费启用前硬门禁

本文是计算交易结算手续费从“休眠代码”进入真实资金链路前的强制门禁。它不是实施建议，也不是灰度观察项：以下五项全部关闭并取得可复核证据之前，不得激活费率、不得给订单锁定收费策略、不得注册手续费路由或 worker，也不得从现有结算流程旁路调用 `PostgresSettlementFeeStore`。

## 当前休眠安全状态

截至当前实现，手续费不会影响线上订单：

- 数据库迁移只创建费率表，不创建或激活任何费率版本；
- 迁移时已有订单全部写入 `grandfathered_no_fee`；
- 当前新订单也由数据库触发器写入 `grandfathered_no_fee`；
- 服务启动、应用装配、API 路由和结算 worker 均未构造或调用手续费 Store；
- 现有真实关账仍执行原两腿结算，`service_fee_credit_micros` 默认为 `0`，净额等于毛额。

这只证明“当前没有收费”，不证明收费链路已经可以启用。任何单独暴露 Store、注册管理或结算 route、让 worker 旁路调用 Store、手工写入 active schedule 或替换订单 grandfather 触发器的变更，都会打破这层休眠保护。

## 启用总原则

1. 手续费必须原子替换真实关账，不能成为真实关账前后的附加步骤。
2. 对 `grandfathered_no_fee` 订单继续走原免手续费语义；只有在明确切换点之后创建并原子锁定费率的订单才可收费。
3. 同一数据库事务必须完成订单到期校验、订单与验收锁定、毛额确认、三腿记账、供应商结算记录、手续费评估、月累计更新和订单关闭。任一步失败必须全部回滚。
4. 休眠期间禁止添加任何可到达手续费 Store 的 API、定时任务、消息消费者、后台按钮或脚本入口。
5. 五个门禁的验收证据必须来自真实 PostgreSQL 并纳入持续测试；仅有单元测试或 PGlite 通过不能作为并发和锁行为的最终证明。

## Gate 1：真实关账只能有一个原子入口

### 风险

现有订单关账会把供应商待结算账户的毛额通过两腿交易转入可用账户，并写入供应商结算记录和关闭订单。手续费 Store 当前又能独立发起“待结算扣毛额、供应商可用入净额、平台收入入手续费”的三腿交易，但不会校验七天可结算时间，不会写入真实供应商结算记录，也不会关闭订单或排除已经完成的两腿结算。

如果把两条路径并列接通，同一订单可能被重复借记和重复到账。供应商待结算账户余额不足时，结果不是安全跳过，而可能是主关账持续失败；该账户若还有其他订单形成的余额，则重复结算甚至可能成功。

### 必须实现

- 对收费订单，三腿交易必须在现有真实关账事务内取代两腿交易，不能由独立 Store 在事务外补扣。
- 关账入口必须锁定订单、验收、保留款、供应商结算唯一记录、收费策略、供应商月度期间和涉及的全部账户，并采用固定锁序。
- 必须复用现有到期、订单状态、退款/售后阻断、毛额和验收关系校验。
- `kai_credit_supplier_settlements` 必须保存毛额、手续费和净额，并唯一关联这笔三腿账本交易；订单关闭仍必须由该结算记录证明。
- 数据库对免手续费订单只接受原两腿语义，对收费订单只接受三腿语义，且二者由不可变订单收费策略明确区分。
- 同一订单、验收、结算来源和账本交易只能各自成功一次；已关账订单不得再次进行手续费评估。
- 手续费 Store 不得被 route、worker 或后台工具直接调用。若保留该类，其写操作必须只能接受真实关账事务的数据库 client 和已锁定上下文，不能自行开启独立资金事务。

### 验收证据

- 集成测试证明免手续费订单仍为两腿、费用为零、净额等于毛额。
- 集成测试证明收费订单只产生一笔三腿交易、一条供应商结算记录、一次手续费评估和一次订单关闭，三腿总和为零，毛额等于净额加手续费。
- 在“手动结算与 worker”“两个 worker”“结算重试”“结算与退款”并发屏障测试中，同一订单只关账一次，无重复到账、无重复评估、无唯一键异常泄漏。
- 到期前、售后待处理、毛额不一致、关系不匹配和任一写入故障均导致整笔事务回滚，订单和全部账户余额保持不变。
- 启动依赖图和路由清单证明不存在手续费 Store 的旁路入口。

## Gate 2：退款后累计费必须等于保留净交易量的累计函数

### 风险

结算使用累计函数差额 `F(after) - F(before)`，但当前退款按指定原评估的 segment 冲回手续费，再把供应商该月累计毛额直接减去退款毛额。若退的是较早进入高费率档的订单，而较晚订单已经享受低费率档，保留下来的手续费会低于 `F(退款后净交易量)`，后续交易还会继续从被降低的累计位置享受低费率。

必须固定以下回归例：

- 第一档 `0–50 KAI`，费率 `1%`；第二档费率 `0.8%`；
- 同一供应商、同一自然月先后结算两笔，每笔 `50 KAI`；
- 第一笔手续费为 `500000` 微卡时，第二笔手续费为 `400000` 微卡时；
- 之后全额退第一笔，退款后净交易量为 `50 KAI`；
- 此时保留手续费必须等于 `F(50 KAI) = 500000` 微卡时，不能保留为 `400000` 微卡时；
- 因而不能只冲回第一笔的 `500000` 微卡时并原样保留第二笔费用，必须通过全期间 LIFO、重新定价或明确差额调账恢复累计函数不变量。

### 必须实现

- 定义并固化同一供应商、费用类别、上海自然月内的唯一退款计费不变量：任意结算和退款序列结束后，累计保留手续费必须等于适用策略下对净交易量的累计费用。
- 退款不能只在单个 original assessment 内做 LIFO；必须处理同期间多个 assessment 的相对档位变化。
- 选择并实现一种可审计方案：全期间逆序释放、对保留 assessment 重新分段并生成差额调整，或数学上等价的期间重算方案。
- 跨月发生的退款必须调整原结算期间，同时记录实际退款时间；不得把原月成交量误记为退款发生月，也不得静默改变历史账单。
- 费率版本跨越期间或同月发生切换时，必须有确定、可复算的重定价规则，不能依赖处理顺序偶然得出结果。
- 任何退款不得超过原成交可退毛额、原已收手续费或期间当前净交易量。

### 验收证据

- 上述两笔各 `50 KAI`、先退第一笔的回归测试精确断言保留费为 `500000` 微卡时。
- 覆盖先退后单、先退前单、部分退款、多次拆分退款、多个订单交错退款、全部退款、跨月退款和费率版本切换的属性测试。
- 对同一最终净交易量的不同拆单、结算顺序和退款顺序，断言期间最终保留手续费一致。
- 账单能展示原评估、退款冲正、重新分段或差额调整之间的可追溯关系，且期间汇总可从不可变明细重建。

## Gate 3：同键并发必须稳定 replay

### 风险

当前实现先查询幂等记录，再获取供应商月度期间锁。在真实 PostgreSQL 的 `READ COMMITTED` 下，两个同键请求可同时查到“尚不存在”；后一个请求随后虽然会被期间锁串行化，却可能最终撞到账本或评估唯一约束并向调用方暴露数据库异常，而不是返回 `replayed` 或明确的 digest conflict。

### 必须实现

- 在任何资金、期间和账户写入之前，先对 `(idempotency_owner, idempotency_key)` 原子 claim 或获取可证明唯一的锁。
- 相同 owner、key 和 payload digest 的任意并发请求只能有一个创建者，其余请求在创建事务提交后必须返回同一 assessment 和完全相同的结果，状态为 `replayed`。
- 相同 owner、key 但不同 payload digest 必须稳定返回业务冲突，不得复用旧结果，也不得暴露唯一键异常。
- 相同 source identity 的并发请求也必须收敛到 replay 或明确冲突，不能先发账本再靠后续唯一约束回滚作为正常控制流。
- 统一文档化 schedule、order、idempotency claim、period、assessment、segment 和 account 的锁序，并验证结算、退款和费率激活之间无死锁环。

### 验收证据

- 使用两个及以上真实 PostgreSQL 连接和显式并发屏障，证明同键同 digest 仅一笔账本、一个评估、一次期间累计更新，所有其他调用返回 replay。
- 同键不同 digest、同 source 不同 key、结算与其退款并发均返回稳定业务结果，不泄漏 SQLSTATE `23505` 或死锁错误。
- 高并发重复运行测试无余额漂移、无孤立 pending transaction、无期间版本丢失。
- 锁序测试或运行时观测证明没有相互倒置的 `FOR UPDATE` 获取顺序。

## Gate 4：数据库必须独立证明费率、账本和 segment 完整

### 风险

当前数据库触发器能检查订单、供应商、收费策略、期间关系和三腿金额是否彼此匹配，但不能证明手续费是按照锁定 schedule 计算的，也不能证明 assessment 的累计起点等于期间当前累计值。账本交易没有被 assessment 唯一占用；segment 只有在实际插入时才触发延迟平衡检查，因此零 segment assessment 可绕过检查。segment 保存的 tier、边界、费率和 exact numerator 也未被数据库证明来自锁定 schedule。

这意味着拥有数据库写权限的其他 Store、脚本或错误迁移可以构造“账本平衡但费率错误”的账单，复用同一账本支撑多条 assessment，省略 tier 明细，或让期间累计与不可变明细分叉。

### 必须实现

- assessment 必须唯一关联一笔 posted 账本交易；该交易不得被其他 assessment 或供应商结算记录重复消费。
- source identity 必须关联真实存在且关系匹配的结算或退款来源，数据库必须校验 order、supplier、acceptance、gross、source kind 和 source id；不能只保存无外键的字符串声明。
- assessment 的 `cumulative_before` 必须等于锁定期间的当前累计，`cumulative_after` 必须由本次毛额或退款原子推导，期间 counter 与 assessment 必须在同一事务中同步更新。
- 数据库必须用锁定 schedule 的不可变 tiers 重新计算或验证总费用；应用层给出的 fee 不能成为唯一事实来源。
- 每个 assessment 至少有一个 segment。segment ordinal 必须从零连续；tier ordinal、上下界和 rate 必须等于 schedule tier；`exact_fee_numerator` 必须等于 segment volume 乘 rate；所有 segment 的毛额和手续费必须分别等于 assessment 总额。
- reversal 必须完整关联原 assessment 和原 segments，allocation 总额必须等于 reversal，累计冲正不得超过原成交、原 segment 或原手续费。
- 供应商账单返回的 schedule version、tier ordinal、边界、rate、exact numerator 和 segment fee 必须直接来自上述已验证的不可变快照；不得在读取时用数组位置掩盖持久 ordinal 缺口。

### 验收证据

- 一组 direct-SQL 负向测试分别尝试：篡改费率、篡改累计起点、复用 ledger、伪造 source、超过订单毛额、零 segment、缺 ordinal、伪造 tier 边界/rate/numerator、少 allocation 和超额冲正；每种攻击都必须由数据库拒绝。
- 正向测试证明应用计算与数据库重算在档位边界、跨档、微卡时舍入和最大允许金额上完全一致。
- 期间 counter 可由不可变 assessments 重建并逐期间对账，重建值与在线值始终相等。
- 账单 API 的 tier 字段逐项等于数据库中经 schedule 验证的快照，并能定位原 schedule 和原/冲正 assessment。

## Gate 5：零手续费微额冲正不得阻断退款

### 风险

累计向上取整和按 segment 比例冲正会合法地产生 `0` 微卡时的手续费差额。例如一笔手续费被拆成多次微额退款时，第一次可能冲回 `1` 微卡时，紧接着的微额退款可能应冲手续费 `0`。当前 Store 要求每次都生成三条非零分录，数据库触发器也无条件要求手续费大于零，因此合法退款会被拒绝；这还与表约束预留的“零手续费 reversal”语义冲突。

### 必须实现

- 明确定义并实现零手续费冲正策略。推荐语义为：当 `fee = 0` 时仍完成买方毛额退款和供应商净额冲回，只省略平台收入腿；账本必须是 posted、两腿非零且平衡，并与 reversal assessment 唯一关联。
- 当 `fee > 0` 时必须保持三腿非零且平衡；不能用零金额占位分录伪装三腿。
- 数据库 CHECK、触发器、Store 和账单模型必须对两腿零费冲正采用同一规则，不得一层允许、另一层拒绝。
- 不得为了凑出下一微卡时手续费而延迟、合并或拒绝用户退款。
- 多次微额退款累计冲回的手续费必须等于一次性退款的手续费；全额退款后原 assessment 的毛额、净额和手续费都必须被精确冲完。

### 验收证据

- 构造连续微额退款，使其中至少一次 `fee = 0`，断言退款成功、两腿平衡、平台收入不变、账单存在可追溯零费 reversal。
- 对同一退款毛额执行一次性退款和多次任意拆分退款，断言买方总退款、供应商总冲回、平台手续费总冲回完全一致。
- 全额退款后，所有 original segments 的 remaining gross 和 remaining fee 均为零；额外 `1` 微卡时退款由业务层和数据库共同拒绝。
- 负向测试证明零费 reversal 不能缺少买方或供应商分录，正费 reversal 不能退化为两腿。

## 最终启用签字包

只有同时具备以下材料，才允许创建首个 active schedule 或替换订单 grandfather 触发器：

- 五个 Gate 的实现变更及逐项验收证据；
- 真实 PostgreSQL 专项测试报告，包含并发屏障、死锁检查和 direct-SQL 负向测试；
- 免手续费旧单与收费新单并存的迁移演练，证明切换点前订单永不追溯收费；
- 真实关账事务图、固定锁序、账本分录模板和失败回滚演练；
- 期间累计与不可变 assessments 的重建对账报告；
- 路由、worker、后台和脚本入口清单，证明不存在旁路手续费 Store；
- 经财务、后端与运营共同确认的首个 schedule 版本、上海时区生效时间和回退方案。

任一证据缺失、仅在内存数据库通过、存在唯一键异常泄漏、账单无法从不可变明细重建，或旁路 Store 仍可到达时，启用结论必须为 **不通过**。
