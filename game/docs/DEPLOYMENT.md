# 单机部署与数据恢复

当前服务端使用单进程 JSON 快照，适合单台主机的小规模发布。不要同时启动两个指向同一 `DOUJOY_DATA_PATH` 的进程，也不要把该文件放在不保证本地原子 `rename` 语义的网络文件系统上。需要多副本、滚动发布或跨主机容灾时，应先迁移到 PostgreSQL。

## 快照格式与写入

- `state.json` 是当前快照；`state.json.bak.1` 到 `.bak.N` 是由新到旧的滚动备份。
- 每份快照包含 `schemaVersion: 1`、保存时间和状态的 SHA-256 校验和。
- 写入先落到同目录唯一临时文件，刷新文件内容后原子重命名，并刷新目录元数据。
- 默认保留三代，可用 `DOUJOY_BACKUP_COUNT=1..10` 调整。增加代数会线性增加每次保存的磁盘写入量。
- 临时写入失败会让当前请求失败，但不会永久阻塞保存队列；修复磁盘空间或权限后，下一次保存仍可成功。

旧版无 `schemaVersion` 的开发快照不会被自动接受。升级前应停止服务并保留原文件；测试环境可以删除旧卷重新开始，真实用户数据必须先编写、审查并离线验证一次性迁移程序。

## 启动恢复

服务启动时依次校验主快照和各代备份。主快照损坏、版本不支持、结构非法或校验和不匹配时不会载入；若存在有效备份，会载入最新有效代并原子修复主文件，同时在标准错误输出 `DouJoy store recovered from ...`。

若主文件和所有现存备份都无效，服务以 `STORE_NO_VALID_SNAPSHOT` 退出，不会用空数据覆盖。此时：

1. 停止容器或服务，先对整个数据卷制作只读副本。
2. 检查磁盘空间、挂载状态、所有者和权限，不要手工修改 JSON 或校验和。
3. 从独立的卷快照恢复整个数据目录，再启动服务并检查恢复日志、登录余额和最近对局。
4. 保留损坏副本用于排查，确认恢复点之后产生的对局是否需要人工处理。

## 运维备份与更新

容器部署必须保留 `/data` 卷，并设置 `DOUJOY_DATA_PATH=/data/state.json`。外部备份应在停止服务后对整个卷做快照，以便主文件与滚动代保持一致；定期执行恢复演练，不能只检查备份任务显示成功。

推荐更新步骤：停止旧实例、备份数据卷、用同一个持久卷启动一个新实例、等待 `/health` 正常，再执行游客登录以外的现有账户冒烟检查。回滚应用版本前先确认旧程序理解当前 `schemaVersion`；不要直接用旧二进制打开新格式数据。
