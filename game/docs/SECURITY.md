# 安全与公平设计

## 服务端权威

- 客户端永远收不到其他玩家手牌，只能看到手牌数量。
- 客户端不能上传发牌结果、角色、倍数、余额变化或胜负。
- 每次出牌重新验证归属、牌型、大小和当前行动座位。
- 动作携带客户端看到的 `expectedSequence`；旧状态请求会以 `STALE_GAME` 拒绝。
- 每个动作携带唯一请求 ID；网络重试返回原结果，不会重复执行。
- 行动超时由服务端时钟判定；客户端不能伪造倒计时或替其他真人提前托管。

## 洗牌承诺

每局使用 Node.js `crypto.randomInt` 实现 Fisher–Yates 洗牌。开局时生成 128 位随机 nonce，并计算：

```text
SHA-256(nonce + ":" + 按顺序连接的 54 张牌 ID)
```

牌局进行中只向玩家返回哈希承诺；结束后返回 nonce 和完整牌序，任何客户端都可以复算并确认牌序在开局后未被修改。`core/fairness.ts` 还会验证 54 张牌不重不漏，并以常量时间比较复算摘要。这个机制证明“提交后未改牌”，不声称可以阻止控制服务端的人在提交前挑选牌序；生产环境应进一步使用独立随机性审计和不可变日志。

## 竞技分账本

- 所有交易至少包含两个方向相反的账户分录。
- 分录总和不为零时直接拒绝写入。
- 对局结算使用 `settlement:<gameId>` 作为唯一键。
- 初始竞技分和每日补助使用独立的平台发行账户作为对应分录。
- 竞技分没有充值、提现、转账或兑换路径，也不能兑换 KAI 卡时。

## 卡时隔离

- CloudPay 计费默认关闭，沙盒订单使用独立文件和醒目标记。
- 游戏竞技分账本不能读取、写入或推算卡时余额。
- 真实卡时支付必须由 CloudPay 权威账本完成，游戏只保存外部订单引用和服务权益。
- 生产启用前必须迁移至 PostgreSQL、校验签名 Webhook、执行账账对账并关闭所有模拟完成入口。

## 上线前安全门槛

- 当前原子快照存储只用于单进程、单机部署；多实例上线前以 PostgreSQL 事务与行锁替换。
- Redis/数据库租约确保一个房间只有一个权威执行者。
- 接入正式身份、设备风控、速率限制、封禁和举报审核。
- 对同设备多账号、固定同桌输送、异常胜率和自动化操作建立风险事件。
- 生产环境只允许 HTTPS，并限制 CORS 到正式 App/Web 来源。
- 对会话令牌做服务端哈希存储、轮换和撤销。
